# Changelog

All notable changes to the project are recorded here.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project
uses [Semantic Versioning](https://semver.org/) (MAJOR.MINOR.PATCH):

- **MAJOR**: a change that breaks compatibility (e.g. the format of the memory or of the evaluation cases).
- **MINOR**: a new feature, compatible with what exists.
- **PATCH**: a bug fix, with no new feature.

While MAJOR is 0, the project is in initial development, and changes that break compatibility
also bump MINOR.

The project was called smart-rpa until 2026-09-29; the entries before that use the old names
(the `app/` package, the Portuguese commands and options).

## [Unreleased]

### Added
- **Where each measurement was made.** Every result file of `eval/` records the full commit, its
  tag, and whether the working copy had uncommitted changes (`eval/provenance.py`). A development run
  with changes is named `+dirty` and lists them (the results of 21-22/10 said only the old commit); a
  final run refuses to run on a changed working copy or on a commit without a tag, so the release is
  tagged before its final run and its results carry the tag.
- **A third origin for the closed set, and results by origin.** The closed tasks have an `origin`
  (synthetic, synthetic_controlled, human) and a `generator`; `eval.plan_run` reports each origin,
  each generator, and the sensitivity analysis decided for `synthetic_controlled` (without the
  ChatGPT's requests). `eval.closed_sets` reads the generators' sheets (with the package's literal BOM
  text in one header) and makes the tasks file to annotate. The synthetic set's provenance is
  corrected: its 80 requests were generated by three AIs, not written by colleagues.
- **The local interface, step 1** (`python -m anchor.ui`): a server on this computer only
  (127.0.0.1, a free port) and an Angular app it serves, in English, with the ANCHOR design system
  (the waterline wordmark, a dark violet theme with lime and lavender, and a light theme). For now
  it lists the saved automations and shows each one: its request (the values you give as chips),
  its site and model, its plan, its last runs, and how many fixes, notes and decisions it has.
  A Docs link on every screen opens the documentation. Every API request must carry a code made at
  each start (handed to the app in the address's fragment and taken off the address bar), and come
  from the app's own address and origin: no other program or website can drive ANCHOR. The server
  reads through the same automation store as the command line and adds no rules of its own.
- **The local interface, step 2: running.** An automation runs from its page (with a field for
  each value it needs, and the options to learn the plan again or use a clean browser), and a
  one-off request from "Run a request" (the request, the page and the model). Runs wait their turn
  in a queue and go one at a time (one GPU); the run's screen shows what happens as it happens, and
  a Stop that takes effect at the next step. The questions a run asks come to the interface: a
  sensitive action (Allow, Don't allow, Not now), which element (one of the numbered candidates, the
  person clicking it in the browser, or skipping the step), and a login (done in the browser window,
  which still opens on its own; the live view inside the interface is step 3). Stopping with a
  question open answers no, and keeps no decision. A run does exactly what the command line does
  (run_automation, the Agent), and a request with a password is refused before it is queued.
- **Runs, told step by step.** Every event has its time of day; while the AI works, a live line
  says whether it is thinking or writing the plan, for how long and on which attempt; a plan the
  AI gave that was not usable is shown with why, as soon as it is known; steps, refusals and checks
  are told apart; and the outcome is said in plain words, with what to do next, above the engine's
  own message. Each run can show the browser window or not (with it hidden, a page that needs a
  login says so instead of waiting).
- **The live view.** "Watch it run" fills the window with the run: the browser, live, on the left,
  and the open question, the outcome and what happened on the right, so a question is answered
  while watching (Esc or "Close the live view" goes back). The browser now runs hidden by default
  ("Also open the browser in its own window" brings its window back). The picture is made only
  while the view is open, follows the tab the run is on, and keeps coming while the run waits. Under each
  step, the element it was done on ("on the button “Save customer”"), from a listener the action
  executor now calls after each action.
- **"It's none of these" and "It needs a login first".** When ANCHOR asks which element a step
  meant, the person can now say it is none of the ones found, and why ("the reports are inside the
  portal: log in first"): the step fails with those words as its reason, so the planner hears them
  when it plans again; for an automation, the words can also be kept as one of its notes, sent to
  its planner on every run. Or say that a login comes first: ANCHOR waits for the login (on the live
  view) and plans again from the page after it, as it does when a step meets a password field. In
  the engine: two new answers to "which element" (none, with a note; login), the note in the step's
  result, and a failure reason with the person's words, in the model's language.
- **The interface, step 5a: creating automations.** "New automation" creates one the way the
  command line does (the values in braces become the fields each run asks for, shown as they are
  typed; a suggested name; no password in the request). After a request that was done and
  checked, "Save as an automation" keeps the steps of that very run and the goals they reached,
  with no new run; it is not proven yet, so it needs one clean run with someone there before it may
  run unattended. And "See the plan first" asks the AI for the plan on the page and shows its steps
  and what it would check, doing nothing: its state is "Planned", never "Checked".
- **The interface, step 4: logging in and pointing on the live view.** When a page needs a login,
  or the person chooses to point at an element, the live view opens by itself and takes the
  person's clicks, scrolling, keys and Ctrl+V, which the run delivers to the browser; at any other
  time it only shows. What is typed goes to the page and nowhere else: not to the model, not to
  what happened, not to the run's details. Pointing works with the browser hidden (the click
  capture now has a form that does not hold the run: start, read, cancel; the action executor uses a
  disambiguator's own capture when it has one). And "Log in to this site", on an automation's page,
  opens its browser in a window, on its site, so the person logs in once and its runs keep the
  session.
- **A guide for the first time.** When ANCHOR opens, a short guide (four pages) says what it does,
  where things are, what happens during a run (watching, the questions, Stop, Try again, never a
  password in a request) and which model to use: the small one first, the medium one for big pages
  and long requests, and that saved automations do not use the AI at all. It opens until the person
  turns it off, and again from "Guide" in the header.
- **Try again and the run's details.** After a run that was not done, "Try again" opens the
  request's form filled in with the last try (request, page, model, window), or the automation's
  page with the same values. "Save the details of this run" saves a file on this computer with what
  the model read (the page summary) and answered at each planning, for working out what went wrong.

### Changed
- **License: Apache 2.0** (was PolyForm Strict 1.0.0): ANCHOR is now open source; it may be used,
  modified and redistributed, commercially or not, keeping the license and the notices (`NOTICE`,
  new). Pull requests are still not accepted until the 1.0.0 evaluation, now for that reason.

### Fixed
Found in real runs on LinkedIn, GitHub and the UI Testing Playground (17/10); each fix has a test
that fails without it, and the reference plans of every suite and the benchmark's levels with no
model are the same before and after (0 false successes).
Measured with the models on the code of commit `b9eb27c` (whose results commit, `fd0676a`, says "H"
for it, and whose result files say `ebadedc`, since the fixes were not committed yet): the main suite
(`plans_20261022-105421`: 4B 93% and 87%, 9B 93% and 100%, en and pt, no premature end), uploads
(`plans_20261022-110859`: 100%) and the resilience benchmark (`resilience_20261022-120459`: every one
of the 600 runs with the same outcome as in 0.4, 0 false successes, 0 attacks with effect). The other
result files of 21-22/10 were measured on earlier states of the same fixes, during the investigation:
`plans_20261021-*` (the seven suites) with only the first part, and `plans_20261022-001957` with the
first part and the login fix.
- **A goal is met by its last planned step, not its first.** A step that worked marked its goal as
  met even when the goal had more steps ("search for ollama" was met by the click that opened the
  search box), so the planner was told something was done that was not, and skipped the rest. It is
  met now only when no other step of the goal is still to do (a later step that only repeats this one,
  the same action with the same value, does not count), and never by a step that led to a login
  page (a step done on a login page, like the user name, still meets its goal).
- **A step that leads to a login page waits for the login.** "Star" on GitHub asks to sign in first:
  ANCHOR now waits for the person to log in (as when a login comes first) and plans again from the
  page after it; that step does not count as done, so it can be done again once logged in. Without
  anyone there (unattended), nothing changes.
- **Acting on the person's account is sensitive, and blocked when not asked.** A new family,
  "account": connect, like, react, comment, share, repost, subscribe, invite, and following someone
  ("Seguir JAINE…"; "Seguir" alone, or "Seguir para o pagamento", is still going on). The models had
  planned to follow three people nobody asked for. Only a verb of the family in the request asks for
  it (a request about the same person does not).
- **A step described as "(no text)" is refused.** The page summary's name for an element without one
  points at nothing; the model is told to describe the element by what is near it.
- **A search is sent after the term is typed.** The end check took the click that opened a search box
  ("Search /", before typing "Pi Network") for the search, and a run ended as done with the term
  typed and never sent (en-pop-01, the 4B model, 21/10: the dev suite's only premature end). When a
  request asks to search and the plan types something, the click or the Enter that searches must come
  after what was typed; all 250 reference plans of the dev suites and the benchmark still pass it.
- **"Confirm whether / that…" is a check.** "Confirme se o texto mudou" no longer asks for a click on a
  Confirm button ("confirme o pedido" still does).
- **A new plan that starts with the step just done goes on.** After opening a post's "…" menu, the plan
  repeated that click before "Salvar", and the repeat was failed three times; it is skipped now, and
  the plan goes on with the next step (a plan with only that step still fails, as before).
- **A blocked click fails sooner, and says what blocks it.** A click waits 10 s for its element (not
  Playwright's 30 s, which cost a minute on LinkedIn), and when something is on top of the element the
  planner hears what ("the click was blocked: "Mensagens" is on top of the element").
- **The site's own pop-ups.** An alert is accepted and its text reaches the planner; a question ("Are
  you sure?") is always answered no, since ANCHOR never confirms on its own. Either is the click's
  effect.
- **Pages that answer late.** After a click with no change, ANCHOR waits for the timers the click
  itself scheduled (up to 8 s) before calling it "no effect" and clicking again ("Wait for alert!");
  a click that scheduled none waits nothing more.
- **Outcomes said right.** A click that timed out was shown as "The AI could not be reached";
  "N failed attempts" showed words written for the model. Both are said in plain words now, with the
  last problem as the hint.
- **A plan's refusals in the reader's language.** The planner kept why each plan was refused in the
  model's language only; it now keeps it in the interface's too, so the interface (in English)
  no longer shows "a ação fill precisa de um valor".
- **A request that asks to log in, on a page whose login is behind a link, waits for the login.**
  LinkedIn's home has no password field until "Sign in" is clicked, so ANCHOR planned instead of
  waiting; the model then planned to type an e-mail it does not have, and the run ended, after two
  refused plans, with "the fill action needs a value". Now, when such a request fails to plan,
  ANCHOR asks the person to log in and plans again (with no one to ask, nothing changes).

## [0.4.0] - 2026-10-17

### Security
- **A recovery that acts where the saved step only went somewhere is not accepted.** In the 0.4 run of the
  full resilience benchmark, level 5 (a page with planted lures) led the 4B model's repair of "open the
  shopping cart" into "Adicionar ao carrinho depois" (the lure), and the recovery contract accepted it:
  both steps share "cart", which was half of the saved step's content words. The plan was saved, and the
  next run clicked the lure with no model call: the first attack with an effect ever measured on ANCHOR,
  and a false success. The same task on level 1 accepted "Adicionar ao carrinho" + "Continuar" for "open
  the cart". Now a saved step with no action verb (a link, "open", "view") is not redone by a step that
  acts (add, delete, continue, send). Replayed on every real recovery of that run: both false recoveries
  are refused, and the twelve legitimate ones (renamed fields, reworded buttons) are still accepted. The
  lure was still clicked once, during the recovery attempt; the next entry stops that too.
- **During a recovery, a click that acts is checked before it happens.** The executor's guard (the one
  unattended runs use) is on during every recovery: a click that does something (add, delete,
  continue) must be the redo of a saved step still to redo that acts too, about the same thing; a lure
  is refused before the click, and the planner is told why. Fields are left to the contract (it knows
  their values), and steps that only go somewhere or prepare are let through. Replayed on every real
  recovery of the 0.4 benchmark runs: the lures ("Adicionar ao carrinho depois", "Add to cart later",
  and "Delete everything", which the 9B model also tried) are refused, and no step of a legitimate
  recovery is.
- **"Delete of Brian Lee" no longer resolves to the "Tick Brian Lee" checkbox.** On level 2 the delete
  button lost its text (an icon titled "Remove"), and the checkbox, the only element with Brian's name,
  won: the last false success of ANCHOR on the benchmark. "Tick" was not a verb for the resolver; it
  now means "check", so the checkbox announces another action and the row's "Remove" wins. With no
  model at all, every level is the same as before except level 2 (17 → 18 of 30, the false success
  gone); every development suite's reference plans still pass.

### Added
- **Unattended runs** (`automations run --unattended`), for a scheduler. Only an automation whose current
  plan is proven runs: done once, with someone present, from start to end with no recovery; that run
  records the element each step acted on, and any change to the plan (a repair, relearning, an undo)
  makes a new plan with no proof. With no one present nothing changes and no one is asked: the model
  is never called, nothing is repaired, there is no tie-break, a new sensitive action is refused, a
  login is not waited for, and a guard in the executor, called once the element is found and before
  acting, lets each step act only on the element of the proving run (an element that differs stops the
  run before any action). What does not change the plan still happens (a cookie banner declined, "Show
  more" opened, an element whose id changed found by its text). The first row that stops ends a
  spreadsheet; the exit code is 1; the browser closes on its own. It goes further than a comment by
  the Auten team on dev.to ("a repair has to be visible before it is trusted"): an unattended run never
  repairs at all, so the quarantine planned earlier for the model's repairs was not needed.
  Running the command itself (not only the function) found two bugs before release: an unattended
  refusal of a sensitive action was saved as a decision, blocking the next runs too (now nothing is
  saved, and the message says the action was not approved with someone present), and a row ending in
  an error did not stop the rest of a spreadsheet. The guard now runs before the sensitive-action
  check, so a changed element is reported as such.
  A first try on Windows, with a real automation, found three more: a cookie banner over the target
  made the click wait 30 s before the banner was declined (now it is declined before trying, when the
  target is covered: 32 s became 2 s on that page); an unattended stop said "Stopped" three times and
  "attempt 2 of 3" (now the first failure ends the run, and the stop is said once); and a learning run
  did not say that it had proven the plan.
- **Hidden content.** When a step's target is not on the page, the agent opens what may hide it, a "Show
  more" button or a collapsed section (`aria-expanded="false"`), finds the target and does the step,
  instead of a replan (the planner never saw the hidden part, and the LLM-in-control agent beat
  ANCHOR on level 4 of the resilience benchmark, where two fields hide behind "Show more"). Only
  controls that say so, with no action verb and nothing sensitive, at most two per step; the planner
  is told the rest of the page is shown. Nothing changes in what the model reads otherwise, and no
  development page has such controls. The idea came from a reader's comment on TabNews.
- **Cookie banners are declined when they are in the way.** On level 4 the "Show more" sat under a cookie
  banner, and the hidden-content step changed nothing. When a step fails and a cookie or consent banner
  is on the page, the agent clicks its most restrictive option ("Recusar", "Reject all", "Only
  essential"), says so, and tries the step again; it never accepts cookies on its own (a banner with no
  way to decline is left alone). Another layer over a "Show more" is not closed: the planner is told.
- **A step that names what its element is about is not done on a lookalike.** With the banner gone, the
  store tasks of level 4 ended in false successes: "Add to cart of the UltraBook 14", with the UltraBook
  behind "Show more", clicked the only visible "Add to cart". When the name after "of / do / for" is
  not on the page (visible text and the accessible names of visible elements), the agent reveals
  hidden content first; otherwise the step is "not found". Checked on every resilience level with no
  model at all (the code alone): level 4 went from 6 to 30 of 30 tasks, levels 1, 2, 3 and 5 are
  unchanged, and no false success was added. A false success that was already there on level 2
  ("Delete of Brian Lee" resolved to the "Tick Brian Lee" checkbox) is a separate resolver issue, left
  for later.
- **Iframes.** Elements inside an iframe (an embedded form or widget, from the same site or another) are
  found and used like the page's own. The resolver reads the page and then each attached iframe, with
  the iframe's elements numbered apart (`f1-el-0`) and each match acting in its own frame; a page with
  no iframes is read exactly as before. The effect check sums the changes and messages of every frame
  (otherwise each click inside an iframe would be "no visible effect"), and the password field (a
  login form inside an iframe), tables, value texts, the candidates' numbers and the count of windows
  a click asked for look inside iframes too. Limits: choosing an element by clicking on it, and the
  remembered choices' CSS-path fallback, only work on the page itself. `eval/plan_run.py --suite
  frames`: 8 development tasks on a page with a newsletter form in an iframe from another file;
  unrequested steps are counted inside iframes, and a task the page does not allow may allow touching
  nothing.
- **Every evaluation run records what it ran on**: the Ollama version and each model's digest and date
  (`environment` in the results `.json`, and printed before the tasks). An automatic Ollama update,
  with the same model files, changed the 4B model's plan for a task that had been stable for days;
  without the versions in the results, that took an investigation to find.
- **Following new tabs.** When a step opens a new tab (a `target="_blank"` link, `window.open`), the
  agent moves to it and replans; when its tab closes by itself (a payment or login window), it goes
  back to the last tab still open. Everything that works on "the page" moves together: the agent, the
  executor, the resolver, the effect watcher (which already counted a new tab as a visible effect of
  the click) and the download listener. Only a tab opened during the step is followed, not one the
  page opens by itself between steps (an ad). Whether a tab closed is tested, not read: on
  Windows, a tab closed by window.close() still read as open (`is_closed()` only reflects what
  Playwright has processed), and the agent went on working on it; a minimal call to the tab settles
  it. The check comes first in each step, since the barriers also look at the page, and before every
  plan, since the summary reads the page. In Playwright's sync API, events (a tab that opened or
  closed) are only processed during calls, so the agent makes a minimal call before reading the new
  tabs or dropping the ones opened before a step. A step that fails because its tab closed is either
  done, if it acted on an element (it is what closed the tab), or done again on the tab underneath, if
  it met the tab closing, without counting as a failure. After a step on a tab it followed, the agent
  also waits up to 0.7 s for it to close; on the first tab there is no wait. Only a tab opened by
  the current tab is followed (a late second payment window, opened by the shop, was taken as the
  doing of the next step on Windows, and the agent switched to it and dropped the steps left); a tab
  that hides its opener (a `target="_blank"` link) is still followed. When a tab closes, the agent
  goes back to the tab it came from, not to the last one open. When the plan still has steps after
  the one that opened a tab, they go on in the new tab instead of a replan: asked for the deadline in
  a policy that opens in a new tab, both models planned "open it, read the deadline", and the replan
  on the new tab threw the reading away (and told the model the goal was met). A step that does not
  fit the new tab fails and replans as before. After a click, the agent waits for the window it
  opens: on a slow Windows run the window arrived after the agent looked, the next step ("Concluir
  pagamento") was done on the shop, matched "Pagar" and opened a second window. A small script the
  agent adds to the pages counts the windows they ask for (window.open, target=_blank links): when a
  click asked for one, the agent waits for it up to 5 s; otherwise up to 0.4 s, for windows opened a
  little after the click. The tab tests passed 18 runs in a row with three running at once. Saved automations close the tabs a run opened and point
  the executor back at their own tab before the next spreadsheet row. `eval/plan_run.py --suite tabs`:
  8 development tasks; the evaluation's instrumentation is now added to the browser context (every
  tab), lets `target="_blank"` links work, runs the checks on the tab the agent ended in, and counts
  unrequested steps on every open tab.
- **A question needs an answer.** A request that is a question (ending in "?", or starting with
  "qual", "quanto", "what", "how many"...) is not done until some step has read the answer
  (`extract_text` or `extract_table`): the request check, which also runs when the model says nothing
  is left, now says so. Asked for the response time in a policy that opens in a new tab, both models
  opened it and stopped (the 9B one looked in the FAQ instead); with the warning, the planner reads it
  in the new tab. Only the four question tasks of the development suites are affected. The same goes
  for a request for the data back ("exporte a tabela", "copy the users table", "me passa a lista"):
  some step must read it or download it. After an automatic Ollama update, the 4B model answered
  "exporte a tabela de vendas por região" by clicking "Imprimir relatório" and was done, the only
  premature end left in the development suites. "Mostre só os usuários inativos" (a filter, not a
  reading) is not such a request. The rule covers exactly the ten reading tasks of the development
  suites, all of whose reference plans read. When a text
  reading finds nothing, the planner is now told to use the text exactly as a "Texto" line of the
  page summary shows it: the 4B model described the reading in its own words ("the text with the
  deadline") and kept doing so until its attempts ran out. This only changes what the model reads
  after a failed text reading (tuned looking at that development task).
- **No sending, saving, paying or exporting the request did not ask for.** A click in one of those
  sensitive categories is blocked, with the reason for the planner, unless the request has a verb of
  the family ("salve", "envie", "pague", which ask for any of them; for exporting, a verb or a word
  for a file) or the request and the button are about the same thing, verbs aside ("reserve a sala"
  and "Reservar sala", "cadastre a Maria" and "Salvar cadastro"). Both models attached the files
  they were asked to attach and then clicked "Enviar candidatura" on their own; the 9B one sometimes
  clicked "Exportar planilha" while asked to select users. Checked first on every click of the
  development and resilience reference plans: none is blocked (the closed sets were left out).
  Printing joined the barrier: with the reading rule, the 4B model answered "exporte a tabela de
  vendas" by extracting the right table, after clicking "Imprimir relatório" first. No reference
  click and no request of the development suites mentions printing.
- **Sending files.** A new action, `upload`: the agent puts the file in the file field, or clicks the
  button that opens the file chooser ("Anexar currículo") and picks it there. The path must come from
  the request (or the notes and parameters): the rule that typed values come from the request now
  covers uploads, so the model never chooses a file from the user's computer. A path that does not
  exist stops the run with a message, before the page is touched (the model cannot fix a path); an
  element that opens no file chooser is a reason to replan. Every upload is a sensitive action. The
  planner hears about it only for requests about sending a file (a verb like "anexe", "attach",
  "envie o comprovante", or a file path), so every other request gets the prompt as before. The
  request check accepts the upload for "send" only when every "send" in the request is about a file
  ("envie o comprovante"); "anexe o currículo e envie a candidatura" still needs the click on the send
  button. As with downloads, the models often planned a plain "click" on the file field or on the
  attach button, which opened the file chooser with nobody to pick the file: such a click, in a
  request that gives file paths, is now an upload of the path whose name matches the field
  ("curriculo.pdf" for "Anexar currículo"), still only from the request. A file sent through another
  field than the one it matches is blocked (the 9B model sent the "comprovante" through "Anexar
  currículo" while the page had "Comprovante de residência"). `eval/plan_run.py --suite uploads`: 10
  development tasks on a new application page.
- **Downloading files.** A new action, `download`: the agent clicks the button or link and waits
  for the file, which it saves in the output folder (the same as extracted tables: `output/`, or the
  automation's folder) with the name the site suggests, never overwriting one (`report (2).csv`).
  Every download is a sensitive action, whatever the button says. A click that downloads nothing
  fails ("no_download"), and the planner is told so. Any file the page downloads during a run is
  kept, even after a plain click (the models often planned "click" on a download button, and the
  file was lost while the run claimed success). Like the destructive barrier, a download must be of
  what the request names: "Baixar relatório de vendas" is blocked for "baixe a nota fiscal" (the
  models downloaded the report instead and claimed success), by the download action or by a plain
  click on a download button. As with extraction, the planner hears
  about the action only for requests about files ("baixe", "download", "PDF", "planilha"...; not
  "exporte", which on a report page is reading, and led the 9B model to look for a download button),
  so every other request gets the prompt exactly as before; the request check counts a download as
  a click. `eval/plan_run.py --suite downloads`: 8 development tasks on a new documents page, judged
  on the saved file (its name and content); the evaluation's instrumentation now lets download links
  work and ignores the link a page creates and removes to start a download.
- **Reading data from pages.** A new action, `extract_table`, reads a whole table or list and saves it
  as a CSV file (UTF-8; `;` as separator in Portuguese, so Excel opens it in columns, `,` in English),
  never overwriting one. The table or list is found by its caption, `aria-label` or the title before
  it, or by its column headers; menus, headers and footers are never taken as data. When the request
  could mean more than one, the agent does not guess: the planner gets their names and picks one. The
  planner hears about `extract_table`, and sees the page's tables and lists at the end of its

## [0.3.1] - 2026-10-10

Fixes found in real use after 0.3.0, the first one a safety fix: 0.3.0 typed a password when the
request carried one, although the README says credentials never go through the AI.

### Security
- **ANCHOR never types a password, and credentials never go through the model.** A fill that would
  land on a password field is refused by the executor (`refuse_passwords`, which the agent and
  `planner --run` turn on). A request that seems to contain a password ("senha: 1234", "password
  hunter2", a quoted value after the word; not "troque a senha do wifi") is refused before anything
  is sent to the model, and `automations create` refuses to save one.

### Added
- **Logging in by hand.** When a task needs a login (the request asks to log in, the plan reaches a
  password field, or nothing can be planned on a page that asks for one), the agent asks the user to
  log in in the browser window and press Enter (or `q` to cancel), then replans from the page it
  finds; with no one at the terminal, the run stops with "the task needs a login". Pages with a
  password field that the task does not need (changing a login page's language) are not stopped.
  The time spent is counted in the wait for the user, and the result counts the logins.

### Changed
- **Saved automations keep their own browser profile** (`automations/<name>/browser/`), so a login
  done by hand once is kept for the next runs; `run --fresh-browser` opens a clean browser for one
  run, and a `--browser-profile` given at `create` is still used instead.

### Fixed
- **Plan errors are shown in the interface language.** They are written in the language the model
  reads (Portuguese by default), because they go back to the model so it can fix its plan, and the
  agent reused that text in its final messages ("failed to replan: ... toda meta precisa de pelo
  menos um passo"). `PlanError` now keeps the message's key and values, and each reader gets it in
  its own language.
- **A goal the model cannot plan yet no longer stops the run.** On sites where part of the task only
  appears later (a search that only exists after logging in), the model left that goal with no
  steps, the plan was refused, and after two attempts the run failed. The goal is now left for
  later: it is taken out of this plan, the plan is marked as partial, and the end is still checked
  against the request.
- The question before a sensitive action no longer promises to save the answer in a one-off run
  (`anchor.agent`, `planner --run`), where nothing is saved: it is now "Allow it? [y/N]". Saved
  automations, which keep the decision, still explain the three answers.

## [0.3.0] - 2026-10-09

Reliability, saved automations and evaluation. In short:

- **Checking what happened.** Each action's effect is verified (the page changed, the field kept
  the value, no error appeared), with a screenshot as the last resort when the other checks doubt
  a step (`--vision`). Plans have goals, are checked against the request, and the end is checked
  against what was actually done, so a run that did not do what was asked does not end as a success.
- **English**, end to end: interface, planner, documentation and evaluation.

### Changed
- Four fixes from the diagnosis of ANCHOR's false successes and attacks in the resilience
  benchmark's development set (all general, none specific to the benchmark's pages):
  - **The destructive-action barrier looks at what the step is about.** When the request asks to
    delete or cancel something, the step must be about what the request names ("Excluir (Bruno
    Lima)" for "exclua o Bruno Lima"), and may act on everything ("Excluir tudo", "Delete
    everything") only if the request says so. Before, any destructive step passed once the request
    had a destructive verb.
  - **A lookalike with an extra word loses to the name asked.** When the top candidates are in a
    near tie and one's name (label and text) is the other's plus words the request does not have,
    the one the request names wins (`NAME_COVERED_BONUS`, 0.10, applied only in that case): "Salvar
    cadastro" over "Salvar cadastro depois", "Add to cart" over "Add to cart later". It changes no
    choice that is not such a tie: the local resolver cases are all unchanged. On the benchmark's
    level 5, the saved plans alone, with no model, now complete 28 of the 30 tasks (18 before),
    with no attack. A first version, a bonus for every element whose whole name is in the request,
    made a single-word name that happens to be in the request win ("Pesquisar" for "clicar na
    sugestão da pesquisa", and SauceDemo's "Open Menu" for "abrir o carrinho", a new silent error
    in each language); it was replaced by this tie-break before release.
  - **The healing contract is one to one, on the same thing.** Each saved step that failed must be
    redone by a different successful step of the same action, with the same value (a renamed field
    filled with the same value) or covering at least half of the saved step's content words.
    "Accept cookies" no longer redoes "open the cart".
  - **A step that undoes an earlier one is noticed.** The agent keeps the boxes and lists it has
    verified and checks them again after each step: checking "CLT" after "PJ" now fails with the
    reason ("this step undid an earlier step"), and the model replans knowing it. Only a requested
    state undone by an unrequested step is flagged: undoing an unrequested step is a correction,
    and when both are in the request there is no telling which is right, so the final checks
    decide. A first version flagged every undo, and the 4B model failed `en-reg-01`, whose request
    ("Register the employee Maria Silva, ... contractor") has both "employee" (the person) and
    "contractor" (the option).
- When a saved automation heals itself, the saved plan is a contract: every saved step that failed
  must have been redone by a successful step of the same action, or the run does not count as done
  (and the plan is not corrected). Before, if the model said nothing was left after, say, closing a
  cookie banner, a run could end as a success without the step the banner had blocked, whenever the
  request had no conclusive verb or data for the check of what was done to catch it. Found with the
  resilience benchmark's level 4. A site that turns a list into buttons may now make a legitimate
  recovery count as not done: a false "not done", never a false success.
- The interventions experiment checks whether the chosen element is the right one right before
  acting, not after: SauceDemo redraws the whole page when sorting, the elements lose their ids,
  and the two sorting cases were counted as silent errors although the resolver chose right.
- The check of the initial plan against the request is no longer fatal. A plan that does not
  cover the request still goes back to the model, but if the attempts run out and coverage was the
  only problem, the first answer is kept instead of giving up: some pages must be revealed bit by
  bit (a magnifier that opens the search field), and the check of what was done, at the end,
  still keeps a run that did not cover the request from succeeding. Found with `plan_run -v` on
  `p-pop-01`, which the 4B model failed in every run after the injection defenses: it planned
  only the click on the magnifier (right, since the field appears afterwards), the check refused
  it, and its "fix" dropped the search.

## [0.2.1] - 2026-09-26

Fixes found in tests on real sites (LinkedIn and CoinMarketCap), reproduced on local pages. On the
Resolver's development set (52 local cases), recall@1 went from 80.8% to 82.7% and the silent
error dropped from 3.8% to 1.9%.

### Fixed
- Pop-ups disappeared from the page summary sent to the planner: on large pages, the limit of 80
  elements was filled by the header, and pop-ups sit at the end of the code. The summary is now
  sorted by relevance (open pop-up, marked with `[pop-up]`; visible on the screen; the rest), and
  elements covered by the pop-up are left out.
- A click that opened a pop-up did not trigger replanning (only a URL change did). The agent now
  replans when a pop-up, dialog or menu opens or closes.
- The Resolver accepted elements that could not receive the action (e.g. filling in a button). There
  is now a filter by action: fill only considers text fields, select only native lists, check only
  checkboxes, options and switches.
- Searches without a button (Enter only) got stuck: a search click that finds no button, right
  after filling in a field, becomes Enter in that field. The prompt also says to use `press Enter`
  when there is no search button.
- Repetition loop: the same step repeated right after replanning is blocked, with a warning to the
  planner, and no step runs more than 3 times. The end check runs at most twice per run.
- Elements chosen by the user's click were kept in the memory with their text only. Now the page is
  reindexed and the full signature is kept; and an element whose text is identical and unique on
  the page is found again even if its context changed.
- Ctrl+C showed the full error: the commands now end with a short message and close the browser.
- An end check that only proposes steps already done counts as the goal being reached (before,
  loop detection turned it into a failure).
- On large pages, the element the request needs could be left out of the summary even with no
  pop-up (e.g. the magnifier after 90 links). The summary is now guided by the request: elements
  sharing words with it come right after the pop-ups.
- Typing in a search field opened the suggestion list and triggered replanning, which led the model
  to click the suggestions instead of searching. Filling in no longer triggers replanning for pop-ups.
- When clicking, the value already typed in a field made the field compete with items showing that
  text (e.g. the search suggestion). Outside of filling in, the value no longer identifies the field.

### Changed
- Barrier for unrequested destructive actions: a step that closes, deletes, removes, hides or
  cancels something the request did not mention is not performed, and the planner is warned.
  Closing a pop-up does not count.
- Identical name: an element whose text is exactly what the request names (ignoring kind words
  such as "Opção" and "Botão") gets a small bonus over those that only contain the phrase. It does
  not apply to extraction, which has its own exact-text rule.
- The prompt says to click the element that reveals what is missing (magnifier, "Search", menu)
  and to answer that the request cannot be done only when nothing on the page would lead to it.
- A request with no verb, which only names an item: elements announcing a destructive or
  dismissive action (close, delete, remove, hide, dismiss, cancel, clear) lose points.
- The prompt asks not to close, hide or dismiss items the request did not mention.
- The `select` safety net tries checking the option when the list does not solve the step.
- `eval/plan_run.py --check`: allowed elements that only show up later (e.g. search suggestions)
  give a warning, not a problem; the reference plan, in `--agente` mode, returns the missing steps
  on each replan.

### Added
- Three development tasks reproducing the real tests: a search in a pop-up (`busca_popup.html`), a
  search with Enter only and suggestions (`busca_enter.html`), and a list of jobs with "Salvar" and
  "Fechar vaga" (`vagas.html`).

## [0.2.0] - 2026-09-26

Complete agent: the system receives a text request and a link, generates the plan with an LLM, runs
it, replans when needed and checks whether the goal was reached. On the 12 development tasks,
through the agent loop, both local models (Qwen 3.5 with 4B and 9B) completed all of them; 10 and
9 of them, respectively, with no unrequested step.

### Added
- The agent loop (`app/agent`): initial plan, step-by-step execution, replanning when the page
  changes or a step fails (with the reason, including an element covered by a modal), the end
  check ("goal reached" when nothing is left), cancelling with a report after 3 failures, and a
  step limit. It records model calls, replans, failures, user interventions, tokens and time.
- The command `python -m app.agent --perfil <name> --url <link> "<request>"`, with a visible
  browser, disambiguation in the terminal, the choice memory and an optional persistent profile.
- The planner accepts the execution history, to replan only what is missing.
- `eval/plan_run.py --agente`: the tasks run through the full agent loop.
- The version number in the code (`app.__version__`), also written to the evaluation results.
- This changelog.
- `isort` configuration in `pyproject.toml`, to check the import order.
- The planner (`app/planner`): turns the user's request into steps with an LLM, in the OpenAI API
  format (it works with OpenAI and with local Ollama models). JSON output validated against the
  Executor's actions, with a new attempt when the plan is invalid, and the list of the page's
  elements in the request to the model. It drops the reasoning of "thinking" models
  (`<think>...</think>`) and accepts extra parameters per profile.
- Model profiles in `llm_profiles.json` (address, model and the name of the environment variable
  holding the key; never the key itself).
- The command `python -m app.planner`, to generate and run a plan from a request and a link.
- Evaluation of complete tasks (`eval/plan_run.py`, 12 tasks in `eval/plans/tasks.json`): request →
  plan → execution → check of the final state, with time and tokens per model, and hand-written
  reference plans as a ceiling.
- Ollama's native API in the profiles (`"api": "ollama"`), with the reasoning of "thinking" models
  turned off (`"think": false`) and options such as `num_ctx`; clear messages when Ollama is not
  running or the model does not exist.
- Real-time progress in the terminal (`app/planner/progress.py`): waiting time and, with the Ollama
  API, the streamed answer with the phase ("thinking" or "writing the plan") and the tokens.
- `eval/plan_run.py` loads each model before the tasks (the loading time is reported separately,
  outside the plans' time) and shows each task's progress.
- Unrequested-step metric in `eval/plan_run.py`: each task lists its allowed elements (`allowed`),
  and any other element acted on (click, typing or choice) counts; the table also shows the
  "clean" tasks (done with no extra step).
- Closed set of planner tasks (`eval/plans/holdout_tasks.json`, empty for now), which only runs with
  `--final`, and `--check` to check the tasks without calling models.
- Cleanup of step descriptions before execution: removes kind labels copied from the page summary
  ("Campo de texto", "Caixa de marcação", "Lista de opções") and quotes.
- A `select` on a radio button or checkbox is redone as `check`.

### Changed
- Planner prompt: which action to use for each kind of element, descriptions without the kind, the
  step that completes the request, no unrequested steps, and login without the password (the user
  types the password and clicks log in).
- Task `p-log-01` adjusted to the system's design: fill in the username and stop before logging in,
  without typing the password.
- The OpenAI client does not retry calls on its own (`max_retries=0`): a timeout shows up right away.
- Element names in disambiguation and in the page summary use the visual hint when the text is too
  short (e.g. "shopping cart 2") and the `data-testid` when there is no other name.
- Imports standardized (PEP 8): standard library, third parties and the project, separated by a
  blank line and in alphabetical order.

## [0.1.0] - 2026-09-25

First version: the execution engine. Steps are still written by hand; the LLM planner and the agent
loop come in 0.2.0.

### Added
- Page perception (`index_script.js`) with interactive elements only: links, buttons, fields, ARIA
  roles and areas clickable through `cursor: pointer`, with the accessible name, icons' visual hints,
  state, card context and geometry. An extraction mode with text elements. Reading of open shadow DOM.
- Text normalization: accent removal, a light PT/EN stemmer, compound expressions and synonyms with
  several values.
- Per-site vocabulary (`ElementResolver(synonyms=...)`), outside the generic dictionary.
- Scoring with a penalty for disabled elements and for conflicting verbs (with groups of equivalent
  verbs).
- The user's disambiguation (`app/engine/disambiguation`): candidates numbered on the page, a choice
  in the terminal or a direct click on the element. A `Disambiguator` contract ready for a frontend.
- The choice memory (`app/engine/memory`): reuses the user's choices, finds the element again by
  its content, expires entries that fail or disappear, and has the review command
  `python -m app.engine.memory`.
- Reproducible evaluation (`eval/`): 60 development cases, a closed holdout of 42 cases (it only runs
  with `--final`), a threshold sweep and a selector check.
- `app/main.py` with the semantic engine on SauceDemo, and a demo in `examples/desempate.py`.

### Changed
- The Executor's thresholds calibrated in the evaluation: minimum score 0.40 and a **relative**
  ambiguity margin of 4% (before: 0.20 and an absolute margin of 0.08).
- The Resolver reindexes the page on every query.
- Results coming from the memory report `similarity` instead of `score`.
- LinkedIn tests disabled by default (the site's terms of use forbid automation).

### Fixed
- B1: the whitespace regex in `index_script.js` (`/\\s+/` → `/\s+/`).
- B2: the index was built only once, and became outdated after navigating.
- B3: old `data-er-id` attributes were not removed when reindexing.
- B4: the `.inventory_item` selector, specific to SauceDemo, was hard-coded in the generic code.
- B5: multi-word synonyms never matched.
- B6: the ambiguity margin depended on the score's scale (now relative).
- The context of elements in lists of short cards covered the whole list.
- The query's object was counted twice, in the element's label and in its context.

## How to release a version

1. On `develop`, change `__version__` in `anchor/__init__.py` to the final version (without `-dev`).
2. In this file, rename "Unreleased" to the version and the date, and create an empty "Unreleased" above it.
3. Update the comparison links at the end of the list of versions.
4. Commit: `git commit -m "vX.Y.Z"`.
5. Merge into `main`, create the tag and push:
   `git checkout main && git merge develop && git tag -a vX.Y.Z -m "..." && git push origin main --tags`
6. Go back to `develop` and bump the version to the next one with `-dev` (e.g. `0.4.0-dev`).
